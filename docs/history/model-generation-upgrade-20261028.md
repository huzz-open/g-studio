## 实施中发现并处理的问题

- 标准 Turbo 首次 MPS FP16 常驻预热失败：上游在 GPU 上调用抗锯齿缩放，PyTorch 2.6 的 MPS 缺少 `aten::_upsample_bilinear2d_aa.out`。服务明确标记失败，没有自动 CPU 重试。现在三模型统一固定为 CPU FP32 输入缩放/裁剪/归一化，随后转入启动选定设备上的图像 Transformer；模型从不因运行错误迁移。适配器与 CPU FP32 抗锯齿参考逐元素一致的回归测试通过，标准 Turbo 重启后预热成功。
- 2.1 分层坐标整数截断已在项目适配层修正。解析球面测试现同时包含正负值并保留变化的细化坐标；完整模型质量仍以随后真实推理为准。初次适配器测试曾因类型注解漏导入 `List` 失败，补齐后通过。
- 新增连接测试首次直接修改原始模拟对象，绕过 Vue 响应式更新，导致预期不符。已改成模拟真实 HTTP 返回新的对象；加载可排队及旧服务 ready-only 兼容测试通过。
- Mini 初版 FP16 常驻的五次真实任务完成，实例 ID 相同、loadCount=1；真实运行中取消后同一实例又成功生成花瓶。后续统一输入预处理后须重新跑最终对照，不能复用此前结果为最终版本验收。

MPS driver 分配计数在不同形状/查询批次之间增长，即使释放任务张量和 allocator 缓存也不能将它视为恒定值。Mini 初版五次任务 driver 采样峰值最大约 16.81 GiB，当前张量峰值约 4.94 GiB，系统可用内存最低约 5.06 GiB。它们和 RSS 不是互斥物理内存区，不能相加。启动预算是参数/工作区估计，未承诺任意长序列不 OOM；执行错误始终直接报告。

### Mini FP16 几何退化：本轮验收发现，已修复适配

第一次最终矩阵中的 Mini 五个任务均返回 succeeded，但四视图显示平板/方块，**几何验收不通过**，这些数字不作为最终性能或质量结论。输入 PNG 正常，条件向量及 latent 全有限值，所以仅检查 NaN、GLB 结构或面数不能识别该问题。

受控定位使用同一个花瓶及缓存中间结果：仅将 VAE 或采样改为 FP32 都没有恢复形状；仅将 DINO 注意力计算改为 FP32 也无效。完整 Mini 图像编码器采用 FP32 后，其输出与本轮旧 FP32 基线逐元素一致（RMS 差 0）；再将条件转为 FP16，后续 FP16 采样/解码恢复花瓶形状。全 FP16 条件向量与基线的 RMS 差约 1.808、余弦约 0.211。这里证明的是当前固定 PyTorch/MPS/模型组合的数值问题，尚未定位到具体算子，不能推广为所有 GPU FP16 都不正确。

因此 Mini 在 MPS 上**启动即固定 FP32 图像编码器**，其余采样/解码仍遵循启动选择的精度；不在任务失败后自动重试或切换设备。新增 `imageEncoderPrecision` 明确返回实际编码精度；启动表分别打印采样/解码和各模型图像编码精度。容量预算也计入 FP32 编码器参数及 9 GiB 工作区。标准 Turbo 与完整 2.1 的数学路径没有因该修复变化。修复后的 Mini 重新运行全部素材，旧的平板结果保留在本地 `mini-final/`、`resident-mini/`，仅作为失败证据。

真实控制面记录：Mini 与标准 Turbo 在 preparing 状态提交后立即取消排队，取消调用约 0.65/0.54 ms，执行耗时为零；公共准备继续，模型随后就绪。修复后的 Mini 分阶段执行取消成功，后续花瓶再生成成功。标准 Turbo 最终独立常驻验证中，运行任务在 encode 阶段取消，执行约 0.31 秒后确认；模型保持 ready，下一花瓶成功（API 29.54 秒、执行 29.17 秒），前后实例均为 `f4ab5a0fcf5e414ba67eb39b8d0c700e`、loadCount=1。取消调用响应快不代表所有长算子都可瞬时中断；实际边界在编码块、采样步、解码块及减面前后。

完整 2.1 早期任务在服务退出时终止，重启读回 `failed / interrupted / INTERRUPTED`，没有悄悄恢复队列。最后的常驻服务退出曾出现 multiprocessing semaphore 清理警告；已改为空闲 worker 先关闭 stdin 正常退出，忙碌/无响应 worker 仍有超时后的终止边界。真实标准 Turbo 启动、加载、预热后退出复测通过，退出码 0、无该警告；生命周期九项测试再次通过。
