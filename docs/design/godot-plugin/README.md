# Godot 素材制作插件：工作流、资产模型与技术选型

> 状态：后续插件设计基线，尚未实施。工作流与以部件为核心的方向已在讨论中对齐；数据结构细节、Godot 版本与语言选型仍需验证和确定。
>
> 整理日期：2026-10-28。本文不代表网页已停止维护，也不代表已授权整体迁移。当前实现以源码和 [当前部件格式](../../reference/parts.md) 为准。返回 [文档索引](../../README.md)。

## 1. 产品目标

制作一套方便生产游戏素材的 Godot 插件：帮助用户从 AI 生成或外部导入的图片，得到可直接用于游戏的摆件、动画、碰撞与遮挡区域、光影部件和瓦片集。

插件负责素材整理、生成算法、批量配置与专用工作流；Godot 原生编辑器负责适合它的场景编辑、节点变换、形状精修和资源配置。

迁移的核心收益是直接编辑项目中的资产，避免用户在 Godot 精修后，修改无法被另一套编辑数据表达。实现时应以 Godot 场景和资源保存最终可编辑结果，不能仅把网页界面搬进 Godot，再维持完整的 `.gs` 与 `.tscn` 镜像。

## 2. 核心概念

| 概念 | 职责 | 示例 |
| --- | --- | --- |
| 原始素材 | 保留导入或生成的源文件及来源信息 | 家具合集图片、角色动作表、整张地图 |
| 部件资产 | 可独立命名、编辑和复用的基础素材单位 | 椅子、大树、整张背景图 |
| 部件实例 | 部件在某个场景中的一次使用，引用资产并保存实例设置 | 房间内三把椅子中的一把 |
| 组合资产 | 按用途组织多个视觉元素、引用或规则 | 角色动画集、瓦片集、场景 |

部件是最小的可复用资产单位，不是像素、顶点等最小数据单位。也不要求每张动画帧、每块瓦片都作为独立部件显示在资产库。

一张不切分的图片可以直接创建为部件；切分后的多个结果可以分别成为部件。包含几十个物品的源图可以只保留为来源，不必同时登记为可放置的部件。

部件代表资产，而非一个 PNG 文件。它可以引用整张图片、图片区域或经过像素处理的新图片，并逐步增加适用的能力。

## 3. 素材进入与制作流程

```text
AI 生成图片 / 外部导入图片
             ↓
       检查与清理素材
             ↓
 整图使用 / 自动切分 / 手动切分
             ↓
       确认并创建资产
             ↓
 ┌───────────┼───────────┬───────────┐
静态部件    动画整理     瓦片制作    背景区域
 └───────────┴───────────┴───────────┘
             ↓
    放入场景、精修并验证效果
```

- AI 生成与外部导入是平等入口；AI 和切分都不是必经步骤。
- AI 生成结果、自动切分结果先作为候选，确认后创建正式资产，避免实验结果污染资产库。
- 保存源图与处理参数，允许返回来源继续加工。去背景、拆分等操作不应无提示地覆盖原始素材。
- AI 图片生成是目标工作流入口，不表示当前项目已经实现该入口；现有 AI 服务主要用于几何模型生成。
- 素材可以逐步补充能力，不要求先完成几何、法线等所有处理才能使用。

## 4. 部件的能力与数据归属

| 内容 | 归属与要求 |
| --- | --- |
| 稳定 ID、名称、修订信息 | 部件基础信息，名称与文件位置不应充当唯一身份 |
| 视觉来源、尺寸、原点与对齐 | 部件基础能力；切图后保留必要的原始留白与对齐信息 |
| 碰撞形状 | 可选，可包含多个形状，用于阻挡或检测 |
| 角色遮挡区域 | 可选，可包含多个区域及排序、透明等行为 |
| 法线与材质 | 可选，描述表面光照能力 |
| 几何与投影参数 | 可选，用于体积近似、高级光影与阴影 |
| 来源与处理参数 | 记录源图、裁剪范围或掩码、生成任务与处理配置 |

示例：草丛可以只有图片和原点；石头增加碰撞；大树分别拥有树干碰撞和树冠遮挡；高级光影椅子再增加法线、几何及图像对齐。

碰撞轮廓、角色遮挡轮廓、灯光遮光轮廓和投影几何必须分开表达。可以提供初始复制或生成工具，但不能把它们视为同一个形状，之后强制同步。

### 4.1 资产、实例与场景

- 部件保存共享的视觉内容、形状和默认设置。
- 实例保存摆放位置、旋转、缩放，以及明确支持的局部覆盖。
- 场景保存灯光、环境、相机和不属于单个部件的区域。
- 修改共享资产影响未覆盖对应属性的实例；移动一个实例不修改资产。
- 只想改变某个实例时，使用明确的实例覆盖或另存为部件变体。
- 不在部件中固化某个预览房间的灯光或相机。

### 4.2 身份、版本与重新生成

- 建议正式资产使用独立稳定 ID；图片哈希用于缓存、查重和来源检查。
- 相同图片可以对应不同用途的部件，不应仅凭图片一致就强制合并碰撞、材质等编辑状态。
- 更新图片或重新切分时，区分“更新现有部件”和“创建新部件”，保留明确的关联关系。
- 重新生成几何仅更新相关几何，不能顺带清空手工碰撞或遮挡。
- 重新识别形状应提供候选、替换或新增等明确操作，并接入撤销。
- 调整切片尺寸或原点可能影响已有形状和帧对齐，需要提示并提供可预览的处理方式。

## 5. 四类制作能力

### 5.1 精灵切分、静态部件与动画

精灵切分是创建资产的工具。需要保留网格识别、不规则识别、手工分割、合并、命名、排列和输出等流程。

- 静态物品输出纹理及可选的部件场景。
- 矩形裁剪可通过 `AtlasTexture` 引用原图区域；去背景、不规则掩码等像素修改需要新的图像结果。
- 动画按角色和动作组织，而不是要求用户管理大量散落的帧部件。
- 帧复用视觉来源和对齐机制；需要时可以引用独立部件，但不强制每帧入库。
- 将按行分组、按数量分组、命名、FPS、循环与逐帧检查做成快捷制作流程。
- 建议以 `SpriteFrames` 保存动画结果，通过 `AnimatedSprite2D` 使用；原生编辑器和插件编辑同一资源。
- 帧尺寸、留白和脚底对齐需要明确处理，避免播放抖动。
- 公共碰撞与逐帧碰撞分开设计；不默认给每一帧复制一套完整部件能力。
- 动画资产只提供动作内容，不自动等于角色状态机、移动或攻击判定逻辑。

### 5.2 场景区域：碰撞与角色遮挡

支持部件区域与场景区域两个入口：

- 部件区域：为树木编辑树干碰撞、树冠遮挡，随部件复用。
- 场景区域：整体地图边界、多个物体之间的补充碰撞等，直接属于场景。
- 整张场景底图可作为背景部件并拥有多个区域，无需先切分。

优先操作原生 `Area2D`、`StaticBody2D`、`CollisionPolygon2D` 和 `CollisionShape2D`，让用户在原生视口精修。插件补充区域分类、批量创建、自动轮廓和行为预设。

角色被树冠遮住与物体挡住灯光形成阴影是不同功能。前者仍需排序、材质或遮挡组件；后者由灯光和遮光系统实现。创建多边形本身不自动具备所有效果。

### 5.3 部件光影与场景光影

部件负责法线、几何、材质及默认投射/接收设置；场景负责灯光、环境、相机；实例允许局部覆盖。

基础 2D 光照可评估 Godot 原生灯光、`CanvasTexture` 和 `LightOccluder2D`。当前网页的高级效果还包括代理几何、表面深度与法线烘焙、图像像素位置重建和阴影接收，不能直接等同于普通 2D 遮光多边形。

在确定完整迁移前，验证一种代表性部件的两条路线：采用原生渲染并接受表现调整，或移植特殊材质与渲染流程。编辑器与游戏应尽量使用同一运行时实现；涉及进入区域等运行逻辑时仍需运行场景验证。

### 5.4 瓦片集与地图

- 插件负责从纹理或九宫格生成瓦片、SDF 边缘处理、子瓦片拼接和 47-tile 配置。
- 生成结果进入 `TileSetAtlasSource` / `TileSet`，地形连接规则属于瓦片集。
- 用户使用原生 TileSet 编辑器精修形状和属性，通过 `TileMapLayer` 绘制地图。
- 47 块瓦片作为瓦片集内部内容管理，不要求在普通部件库展示 47 个摆件。
- 稳定关联瓦片位置、资源和生成参数；重新生成不能无条件覆盖用户补充的碰撞与其他属性。

## 6. Godot 内的界面分工

| 入口 | 功能 | 实现原则 |
| --- | --- | --- |
| 素材制作面板 | 切分、动画整理、瓦片生成、法线生成 | 自定义 `Control` 界面、图片画布和算法，输出原生资源 |
| 原生场景视口与辅助面板 | 形状精修、物体摆放、灯光和材质 | 编辑实际节点与资源，复用原生操作 |

可以在一个插件中同时提供两类入口。不能假定所有内置编辑器都能作为可复用控件任意嵌入自定义画布；优先通过公开的节点/资源编辑入口调用原生工作流。

插件修改需要接入撤销/重做、资源变更通知、场景脏状态与保存机制。耗时图像处理和模型生成不能堵塞编辑器主线程；后台结果由主线程安全应用，并检查任务是否已过期。

现有 [Godot 桥接插件](../../../integrations/godot/README.md) 仍是场景区域 `.gs` 与 `.tscn` 的部分双向同步工具，并附运行时遮挡组件，不是本文所述完整制作插件。既有同步能力不能被描述成只有单向导出。

新插件可以提供一次性的旧数据导入。是否继续支持网页双向协作需另行决策，不作为原生插件所有功能的前置要求。

## 8. C# 与 GDScript 选型建议

本节是建议，不是已确定的技术决策。官方文档于 2026-10-28 核对；实施前需固定 Godot 版本和支持平台，不应直接把浮动的 stable 文档当作兼容版本承诺。

| 维度 | 带类型标注的 GDScript | C# |
| --- | --- | --- |
| 插件与节点能力 | 原生支持，适合界面与编辑器交互 | 原生支持，可调用编辑器 API；绑定命名和部分用法不同 |
| 开发环境 | 标准 Godot 即可 | Godot .NET 版及单独安装的 .NET SDK |
| 修改与验证 | 不需要独立的 C# 构建步骤；生命周期变更仍可能需要重启插件 | 脚本变更需构建，随后验证加载与插件状态 |
| 算法开发 | 简单逻辑方便；逐像素重计算需测量并选择合适实现 | 静态类型、集合和独立测试工具适合复杂算法；仍需测量引擎边界调用 |
| 分发 | 更适合希望复制插件即可使用标准 Godot 的用户 | 源码插件会引入 .NET 环境与构建要求，即使用户游戏逻辑使用 GDScript |
| AI 辅助 | 类型标注、版本固定、示例与检查可提供反馈 | 编译器与类型系统提供明确反馈；Godot 专有 API 仍需查证 |

### 8.1 选型原则：AI 开发效率需要先做配对验证

本项目预计主要由 AI 编写代码，因此人工介入次数、限定预算内的完成率和完整迭代时间，应作为语言选型的重要依据。当前不锁定主语言，先进行第 8.5 节的项目内配对验证。

如果两种语言在本项目测试中的表现接近，且目标是向普通 Godot 用户分发，可优先选择带类型标注的 GDScript，以降低安装和分发门槛。这是分发方面的判断，不是已有评测证明 GDScript 更适合 AI 编写。保留独立的算法接口与现有 Python 推理服务，性能热点经过测量后再选择优化路径。

如果目标先限定为自用/团队使用，而且接受统一安装 Godot .NET 和 SDK，则 C# 主体也合理，尤其适合较多图像算法、复杂数据处理和独立单元测试的项目。

不建议仅因为“C# 训练数据可能更多”就决定语言：没有针对本项目的模型正确率对比，无法据此证明 AI 生成的 C# Godot 插件更可靠。语言通用知识不能代替对 Godot 资源、撤销和插件生命周期的理解。

也不建议一开始把 C# 和 GDScript 大量交叉混用。只要编辑器内必需的功能依赖 C#，薄的 GDScript 入口也不能消除 .NET 要求。以后若采用混合方案，应限制在清晰、可测试的模块边界。

### 8.2 C# 编译是否影响启动与测试

- 编译项目脚本不是重新编译 Godot 引擎。
- 第一次构建可能包含依赖恢复；普通修改可以利用增量构建，但不能保证只有单个文件被编译。
- 已有且有效的构建产物通常不需要每次仅打开编辑器都进行全量构建；实际触发条件应在固定版本验证。
- 修改 C# 插件后需要构建，程序集更新与插件对象生命周期是另一层问题。不能承诺所有改动都即时热更新，也不能假定每次都必须关闭 Godot。
- 修改资源和场景不等于修改 C# 源码，不应把所有编辑操作都算成编译循环。
- 将纯算法与 Godot 节点操作分离，可以让部分测试无需启动完整编辑器；资源保存、撤销和视口交互仍需集成验证。
- 当前未在本项目测量编译或重载时间，不给出固定秒数或“几乎无成本”的结论。

如果倾向 C#，先在小型测试项目记录首次构建、重复无改动构建、简单代码修改、资源结构修改后的恢复时间，并验证启停、保存重开与撤销。成本应按“修改 → 构建 → 正确恢复插件 → 验证结果”的完整循环评估。

### 8.3 分发与运行时依赖

编辑器插件依赖和游戏运行时依赖分开设计。若用户导出的部件或场景引用 C# 脚本、自定义 C# 资源类，可能将 .NET 依赖带入游戏运行时；只在制作阶段使用 C# 不等于所有产物都必须依赖 C#。

产物应尽量使用原生资源；确实需要特殊效果时，明确携带的 Shader 和运行时组件。不能承诺删掉全部插件文件后，引用自定义类型的资产仍然有效。

### 8.4 AI 编写能力：公开证据与局限

检索日期：2026-10-28。找到 GDScript 生成和 Godot 游戏开发的公开评测，但未找到足以支撑选型的“同一模型、同一批 Godot 插件任务、同等条件下 C# 对比 GDScript”的直接实验。此处的“未找到”不等于证明不存在。以下为作者公布的数据，未在本项目自行复现。

| 评测 | 作者公布的结果 | 能说明什么与不能说明什么 |
| --- | --- | --- |
| [Godot-Dodo 原始报告](https://github.com/minosvasilias/godot-dodo/blob/main/models/README.md) | 50 道 GDScript 题；早期 GPT-4 的 Syntax 得分为 19/50，GPT-3.5 为 24/50，专门微调的一个模型为 45/50 | 旧模型确有版本/API 混用问题；Syntax 与功能评分分开，评估允许补齐部分用户方法，不应当作严格端到端通过率；没有 C# 对照，不能代表当前模型 |
| [Godot LLM Bench](https://github.com/flockbay/godot-llm-bench) | 2026-10-06 的 15 题结果：GPT-6.1 Sol、Opus 5.5、Sonnet 5.5 首次均为 15/15；Haiku 4.5 首次 11/15，一次修复后 14/15 | 使用 Godot 实际执行检查，说明基础 GDScript 任务可以完成；每模型仅一轮、样本小、没有 C# 对照，也不覆盖完整素材插件的复杂编辑行为 |
| [GameDevBench 论文初版](https://arxiv.org/abs/2602.11103v1) | 2026-02 初版包含 132 个任务；加入图像/视频反馈后，Sonnet 4.5 从 33.3% 提升到 47.7% | 说明验证与视觉反馈会影响完成率；这是历史版本数据，不是当前排行榜，也不是语言对照实验 |

这些评测任务、模型、时间和评分规则不同，不能把它们的百分比直接拼成模型进步曲线，也不能跨评测推导 C# 与 GDScript 的差距。

结论：

- 对 AI 不熟悉 GDScript 的担心有历史依据，但当前基础任务评测不支持一概认定 AI 无法可靠编写 GDScript。
- 基础任务成功不能证明复杂插件开发可靠，尤其不代表撤销、保存重开、资源共享和编辑器生命周期已解决。
- C# 公共代码多，不等于 Godot C# 编辑器插件训练样本多；公开仓库数量也不能直接当作某个模型的实际训练分布。
- C# 代码执行性能与 AI 生成正确率是不同指标，不能互相替代。
- 能否读取真实报错、运行测试和检查预览，是需要与语言一起评估的开发条件。

### 8.5 项目内配对评测方案（尚未执行）

选择五项代表性任务，分别用 C# 和带类型标注的 GDScript 实现：

1. 图片网格切分，保存切片资源并验证像素范围。
2. 创建动画资源，支持帧率调整和预览，并验证保存后的帧顺序。
3. 创建碰撞多边形，支持撤销/重做，保证节点和形状状态一致。
4. 保存部件，重开项目，验证资源引用、共享资产和实例修改边界。
5. 生成小型 TileSet，验证地形连接规则和试画结果。

固定模型版本、推理设置、Godot .NET 版本（两种语言使用同一引擎）、工具权限、文档访问条件和任务预算。采用等价任务描述、独立初始工程和新会话；不把另一种语言的答案提供给模型。预先制定统一行为验收标准，验证器不因语言改变要求。

建议每项每种语言先独立运行 3 次，共 30 次，作为工程试验；样本仍然较小，不能宣称得到普遍语言优劣结论。分别记录首次验证结果和允许修复后的最终结果，不只挑最好的一次。

记录首次通过率、限定预算内最终通过率、修复轮数、人工介入次数、Token/费用以及包含构建、加载和修错的总完成时间。冷启动依赖准备和日常增量构建分别计时。自动检查之外，保留动画预览、视口交互和插件启停等实际编辑器验证。

决策优先关注人工救场次数和最终完成时间：如果 C# 的构建成本换来了明显更少的修复和人工介入，则有理由选择 C#；如果表现接近，则结合用户安装门槛优先考虑 GDScript。当前没有本项目实测结果，不预判胜负。

## 9. 迁移顺序与验证标准

1. 固定原始素材、资产、实例、组合资产的边界，确定基础资源身份和保存方式。
2. 打通图片 → 切分候选 → 静态部件/动画资源，验证实际素材制作体验。
3. 打通部件/场景区域创建 → 原生形状编辑 → 撤销 → 保存重开 → 再编辑。
4. 独立验证高级光影的代表性部件，再确定渲染路线。
5. 迁移瓦片生成并接入原生 TileSet 精修与地图试画。
6. 最后扩展批量更新、来源追踪、变体和其他高级能力。

必须验证：手工精修不被重新生成覆盖；共享资产与实例修改边界正确；动画帧对齐稳定；插件启停与项目重开后引用有效；已有生成结果不依赖生成服务持续在线；耗时任务取消或过期后不覆盖新编辑。
